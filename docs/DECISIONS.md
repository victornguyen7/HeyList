# HeyList — Decisions

Decisions recorded in the project notes. A reason is listed only where the notes give one.

| # | Decision | Reason |
|---|---|---|
| 1 | Build a website, mobile-first, rather than a native app (native app later) | Works in a phone browser with nothing to install |
| 2 | Keep the app general-purpose; packing before a holiday is only the first use case | It should fit groceries, errands, routines, and any other daily list |
| 3 | Keep the app neutral, for daily use by many groups, not tied to companies | Tested by trying it with three very different users: student, busy parent, older relative |
| 4 | Three ways to work with a list — type, voice, photo | Users pick whichever is easiest at that moment |
| 5 | Voice and photo results are shown to the user to confirm before they apply | — |
| 6 | Sharing is by link, with no account needed to view or check items | Sharing in existing apps usually requires everyone to have an account |
| 7 | Simple interface: large text, few screens, one big talk button, advanced options hidden | Must work for first-time smartphone users |
| 8 | A PayPal order counts as proof of purchase | No receipt scan needed when buying in the app |
| 9 | Settle-up on shared lists uses PayPal invoices | — |
| 10 | Split math, budget totals, and assignment of unclaimed items are done in code, not by AI | — |
| 11 | Use one LLM with vision for both lists and receipts | — |
| 12 | Use the Ollama API for the LLM | — |
| 13 | Use the Web Speech API for voice | — |
| 14 | Use Next.js for the app | — |
| 15 | Use Supabase for lists, receipts storage, and realtime | — |
| 16 | Deploy on Render | Hackathon sponsor; $50 credit received |
| 17 | Use the PayPal sandbox: Checkout JS SDK + Orders API, Invoicing API | — |
| 18 | Use sponsor tools APIMatic Context Plugin, Postman, and Render; Channel3 only as a stretch | — |
| 19 | History is the retention hook: buy again from a past list, plus price memory | — |
| 20 | Server-side logic lives in a FastAPI (Python) backend; Next.js proxies `/api/*` to it | The browser stays same-origin, so no CORS setup and no backend URL exposed to it |
| 21 | Prices live on the server; the client sends item IDs and quantities only | A buyer must not be able to change what they pay |
| 22 | Money is handled in integer cents, converted to PayPal's string amounts without floats | No rounding errors |
| 23 | Call PayPal through the Python PayPal Server SDK rather than raw REST | It is APIMatic-generated, matching the APIMatic sponsor tool; it also handles OAuth tokens |
| 24 | ~~Send each item's ID as its PayPal `sku`~~ Superseded by 28 | The capture response says which items were bought, with nothing stored on our side |
| 25 | Check items off only when the capture status is `COMPLETED` | An order can complete while its payment is still `PENDING` or `DECLINED` |
| 26 | Use the order ID as the capture's `PayPal-Request-Id` | A repeated capture (retry, refresh) returns the first result instead of charging again |
| 27 | Default `BACKEND_URL` is `http://127.0.0.1:8000`, not `localhost` | uvicorn listens on IPv4, while `localhost` can resolve to IPv6 `::1` on macOS |
| 28 | Store each PayPal order (its item IDs and server-computed total) in Supabase when it is created | The capture knows which list items it paid for without trusting PayPal's item fields |
| 29 | Quantity is a column on the list item; checkout charges `est_price_cents` × `quantity` | The quantity is saved with the list, and the browser still sends only item IDs at checkout |
| 30 | Starting lists come from the existing Ollama model; the suggestion is not saved until the person reviews and creates it | Decision 5; the Ollama key and client were already in place |
| 31 | Receipts are read by AWS Textract `AnalyzeExpense`, then matched to items by one text-only Claude Haiku (`claude-haiku-5-5`) call with structured output. Narrows decision 11 for receipts. **Matching part replaced by decision 38** | Textract gives clean line items with a confidence per line; the matching step is cheap text, not vision |
| 32 | A scan only proposes; items are checked off when the person confirms or corrects the matches. Prices come from the stored lines, not the browser | Decision 5 and decision 21 |
| 33 | `est_price_cents` is the price of one unit; the AI is asked for per-unit prices | Checkout already charges price x quantity (decision 29) |
| 34 | The budget check is done in code: the review screen shows how far over budget the suggestion is, and the person unticks items | The AI doesn't reliably keep within the budget (issue 14); decision 10 |
| 35 | Spending on list items is split equally among the list's members; receipt extras are personal and not split; payments are settled with the fewest transfers | Simplest fair default for a shared list; weighted shares can come later |
| 36 | Unclaimed items are shared out greedily, most expensive first, to whoever carries the least estimated cost | Decision 10; good enough at list size |
| 37 | Receipt photos are taken with `<input type="file" capture="environment">` and shrunk to 2000 px JPEG in the browser | Native camera, no library; keeps uploads under the 5 MB backend limit |
| 38 | Receipt matching uses the Ollama model (`OLLAMA_MODEL`) instead of Claude Haiku, and when Textract is unavailable the same model reads the photo itself (it has vision). Replaces the Claude part of decision 31 | The owner chose to keep the Claude API out for now. Textract is still tried first for its confidence scores; a bad photo is not retried with Ollama |
| 39 | When a PayPal payment goes through for an item that something else checked off first (a receipt, a hand tick): whatever was bought beyond the item's quantity is refunded to the PayPal buyer (Payments API refund, idempotent per order and item). A checked-off item has all its units bought, so today that is the order's whole charge for the item, whatever its quantity. A refund that fails is counted toward the buyer in the split (`boughtTwice`) | The owner's rule: extra purchases are refunded to whoever made them. No money drops out of the split, which it did before. Keeping part of a multi-unit purchase needs buying part of a quantity, which isn't built |
| 40 | A `PENDING` capture is stored on the order and holds its items; the person asks PayPal again with a button, which reads the order (`GET /v2/checkout/orders/{id}`) rather than capturing again | Capturing again with the same `PayPal-Request-Id` only replays the first answer. A button needs no public webhook endpoint; webhooks can replace it later |
| 41 | HeyList is presented as one loop (Need → Coordinate → Verify → Settle), not a list of features; the demo follows one shared camping trip from start to finish, while the product stays general-purpose (decision 2) | The AI, the checklist and PayPal make one story only when each step keeps what the one before it established. One focused scenario is easier for judges to follow |
| 42 | Starting lists keep what the person said: a named list is returned exactly (nothing added), stated quantities are kept, and conditions or amounts the AI can't know go in an optional item `note` ("only if nobody has one", "how many? enough snacks for 4 people"). The same name with the same quantity is a repeat and dropped; with different quantities both stay, flagged "listed twice with different amounts" | Quality of the existing AI step, not a new feature (IMPROVEMENTS area 2). Adding up or dropping one of two different amounts would guess silently; a flag lets the person decide |
| 43 | AI quality is measured by `backend/eval_starter.py` on 20 hand-labelled cases (`backend/eval/starter_cases.json`): item recall, quantity accuracy, conditions kept, invented items. It runs only with `--yes`, because each case is a paid Ollama call | A number judges can see instead of "the AI is good". Bounded cost: 20 calls a run, run by hand only (RULES.md) |
| 44 | `money.split()` returns each member's purchases (item, amount, whether it was a kept double purchase), and Settle up shows them under "How this was worked out": paid − share = balance, per person | Every balance must trace back to the purchases behind it (IMPROVEMENTS area 5). Built in the split itself, so the lines always add up to what is settled, and that is tested |
| 45 | On Progress the tick means "done", and paying with PayPal is a separate mode ("Pay for items with PayPal" → choose items → pay, or cancel). Ticking by hand asks what was paid (the browser's own prompt, the estimate filled in; blank = don't know) and can be undone; an item proven by PayPal or a receipt can't be unticked there. The AI review screen lets the person rename items, change quantities and add missing ones before creating the list | One checkbox meant "select to pay", which is confusing on a plain checklist (decision 7, IMPROVEMENTS area 4). Fewer corrections after the AI step means editing in the review, before anything is saved (decision 5) |
| 46 | The UI follows the Figma "Soft glass" screens (mobile 390 px and web 1440 px). One codebase, one URL: below 1024 px (Tailwind `lg`) it is the phone layout with a floating bottom tab bar; above it, the website layout with a top nav, pill tabs and two columns. The device is told by screen width, not by sniffing the browser. Colours are the Figma variables as CSS variables in `app/globals.css`, so the dark ("Midnight") set can be added later as a second block | The owner chose soft glass now and dark later. A breakpoint keeps one page per route, works when a laptop window is narrow, and needs no server logic |
| 47 | The budget is said in the sentence ("..., $200 budget"), as in the design, instead of a separate field; it only counts next to the word "budget". The mic button uses the browser's own speech recognition and only shows where the browser has it | The design has one prompt box. Decision 13 already chose the Web Speech API for voice |
| 48 | Starting lists are sent with **no prompt examples** (`llm.EXAMPLE_COUNT = 0`). 64 hand-written example lists stay in `backend/examples.json`, and `eval_starter.py --examples` measures sending the 3 closest; the 14 that are near-copies of eval cases (`evalOverlap`) are left out of that run. No fine-tuning | Measured, owner's call: the 3 closest lowered item recall (96/98 without, 91/98 with) at 2.3 times the input tokens. Word overlap picked off-topic examples, and the 6–8-item lists made replies shorter (IMPROVEMENTS phase 6). Fine-tuning was dropped: the eval was already near its ceiling, and a tuned model can't run on Ollama's cloud |
| 49 | Price memory: a suggested item takes the median of the last 10 proven unit prices for the same name (`items.name_key`, any list): PayPal captures and confirmed receipts only, not hand ticks; else the last store price chosen for that name; else the AI's estimate. Each suggested item says which (`priceSource`). Buy again uses the paid unit price. Done in code after the AI replies | Real prices make the budget check honest (issue 14) and tie the AI to what PayPal proved (decision 10). Only names and prices are read across lists, never who bought what |
| 50 | Store products come from Channel3 (`backend/market.py`, plain `httpx`, two endpoints: search and product detail). Searched on demand per item ("Find in stores" on Items), never for a whole list; one cap of 100 searches an hour for everyone. Choosing a product reads its price from Channel3 again on the server, keeps the cheapest in-stock USD offer, and makes it the item's `est_price_cents`, so "Pay with PayPal" charges it. Renaming or re-pricing an item drops its product. Nothing is ordered from the store: Channel3's checkout isn't open yet | The owner's choices (IMPROVEMENTS phase 6). The price must never come from the browser (decision 21). Two REST calls didn't justify a new SDK |
| 51 | Store search results are checked by the model before they're shown (`llm.store_matches`): the item, its note, the list title and up to 10 results with their categories go to Ollama, which names the ones that are the item itself. At most 5 are shown. If the check fails the search fails (`MARKET_UNAVAILABLE`); word-only matches are never shown unchecked | Channel3 matches words, not meaning, and has no food at all (live check, 2026-10-27): "milk" returned face cleansers, "eggs" toys. The owner chose an AI check over hiding search on grocery lists or word rules: one more paid call and a few seconds per search, within the same 100-an-hour cap |
| 52 | Optional email login (Supabase Auth magic link, `app/auth.ts`, `/login`). Guests still join a list by name (decision 6). Logged in, the browser sends the access token; `POST /api/lists/{id}/members` checks it with Supabase (`db.user`), saves `members.user_id`, uses the account's name (asked once, then kept in the user's metadata) and returns the same member on every device. A guest can't join under a name an account holds on that list (`NAME_TAKEN`); an account can claim a guest's name. Acting as a member is locked separately (decision 53) | The owner wanted "log in once, never type your name again" without making anyone sign up. Supabase was already the database, so no new service; checking the token through Supabase needs no new Python package |
| 53 | Acting as a member who joined logged in needs that login (`locked()` in `backend/main.py`, `403 NOT_YOURS`): ticking an item off in their name or unticking their purchase, paying as them, and scanning or confirming a receipt as them. Guest members stay open to anyone with the link. Claiming ("Ann buys it") and "Share out the rest" stay open, since anyone may assign who buys (SPEC). Supabase is asked about the token only when the member has an account | The owner asked for a logged-in person's purchases to be theirs alone. Guests have no proof of who they are, so locking them would only lock them out |
| 54 | The backend talks to Supabase over HTTP/1.1 (`db.py` passes its own `httpx.Client`), and Home and History load every remembered list in one request (`GET /api/lists?ids=`, six queries run at the same time, however many lists) | The Supabase client's default HTTP/2 connection, shared by FastAPI's worker threads, failed with `ReadError` when several requests used it at once: History loaded each list separately, so most came back 500 and were hidden (issue 43). Measured locally: 54 of 54 parallel loads pass, was 4 of 18 |
| 55 | Pages show the browser's saved copy of a list first (`localStorage`, `heylist:lists-cache`) and replace it with the fresh one; every list response carries its `split` | Home, History and list pages waited for the backend before showing anything, and Money and Settle up waited for a second request after that. The copy is a per-browser convenience, never the source of truth: it can be missing, it is replaced within about half a second, and every change is still checked by the backend |
| 56 | The browser uses Supabase only for login; lists, receipts and orders go through the FastAPI backend. Checkout sends the buyer to PayPal's hosted approval page and back to `APP_URL`; the Checkout JS SDK stays planned | The backend holds the secret key and checks every change (prices never come from the browser, decision 21), so the browser has no reason to read tables directly. The hosted page already works end to end with the Orders API; the JS SDK would only keep the buyer on the list page (issue 2) |
| 57 | A receipt price or fee that can't be read surely is left blank for the buyer to type in, never guessed: Textract under 90% confidence on the price, or no price; the Ollama reader is told to give none rather than guess. A typed price is saved with `items.price_typed`, so it is self-reported like a hand tick and price memory leaves it out; the browser can only fill blanks, never change a read price (decision 21 otherwise holds). Receipts also read their fees (`receipts.fees`: tax, tip, service, delivery, discounts, other), choosing the taxes and tip that make subtotal + fees = total. A confirmed receipt's fees are shared in proportion to what it bought for the list; the part for its extras stays with the buyer. The review screen says when the lines and fees don't add up to the total | The owner's rule: ask rather than guess a price, and count tax and tip. On 189 English receipts (`docs/RECEIPT_EVAL.md`), Textract's shown prices that were wrong went from 4.0% to 2.5%, with 2.1% left blank; tax read right went from 2% to 97%. Confidence alone catches few wrong prices, but every receipt with a wrong price failed the add-up check. Ollama with the new prompt reads tax right on 98% but leaves only 0.6% of prices blank and shows 5.1% wrong, so it still guesses; Textract stays first |
