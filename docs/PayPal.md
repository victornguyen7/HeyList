## 2. What is built

| PayPal feature | Where | What HeyList does with it |
|---|---|---|
| OAuth 2.0 client credentials | `backend/paypal.py` `_client()` | Signs in with the sandbox app's client ID and secret. The SDK fetches and caches the access token and refreshes it 2 minutes early (`o_auth_clock_skew=120`) |
| Orders API v2: create order | `paypal.create_order()`, route `POST /api/lists/{id}/orders` | One order for the items a person chose, with each item's name, quantity and unit price |
| PayPal wallet experience context | same | `return_url` and `cancel_url` send the buyer back to the list page after PayPal |
| Orders API v2: capture order | `paypal.capture_order()`, route `POST /api/orders/{id}/capture` | Takes the payment after the buyer approves, then checks the items off |
| Payments API v2: refund captured payment | `paypal.refund()`, inside capture | Gives back the charge for a single item someone had already bought (decision 39) |
| Orders API v2: show order details | `paypal.get_order()`, route `POST /api/orders/{id}/refresh` | Asks again about a capture that came back `PENDING` |
| Idempotency (`PayPal-Request-Id`) | both calls | A new UUID on create; the order ID on capture, so a repeated capture returns the first result instead of charging again (decision 26) |
| `Prefer: return=representation` | capture | Gets the full order back, including the capture inside `purchase_units[0].payments.captures[0]` |
| Error details (`debug_id`, `issue`) | `paypal._to_error()` | Logs PayPal's `debug_id` (what PayPal support asks for) and keeps the `issue`, such as `INSTRUMENT_DECLINED` |

The SDK is `paypal-server-sdk` 2.4.0 (`backend/requirements.txt`), PayPal's official Python Server SDK, generated by APIMatic. It runs in `Environment.SANDBOX` only (decision 17); `PRODUCTION` is never selected.

## 3. The checkout flow

1. **Choose.** On the Progress page (`app/lists/[id]/page.tsx`) the person ticks open items. The button shows the total: `Pay $X with PayPal`. It is disabled until the person has joined the list by name, so every payment has a buyer for the split.
2. **Create.** The browser posts `{itemIds, memberId}` to `POST /api/lists/{id}/orders` (`backend/main.py`). The backend:
   - checks every item is on this list, still open, and has an estimated price, and that each is listed once (`400 INVALID_ITEMS` otherwise);
   - reads prices and quantities **from the database, never from the browser** (decision 21);
   - calls `create_order()` with intent `CAPTURE`, currency USD, the total with an `item_total` breakdown, and one PayPal item per list item (name cut to PayPal's 127-character limit, quantity, unit price);
   - stores the order in the `orders` table: PayPal order ID, list, buyer, item IDs, the price charged per item (`prices`) and the total (decision 28);
   - returns `{orderId, approveUrl}`. The approve URL is the order's `payer-action` link (PayPal's name for it when `payment_source.paypal` is set).
3. **Approve.** The browser goes to PayPal's hosted sandbox page. The buyer logs in with a sandbox buyer account and approves or cancels.
4. **Return.** PayPal sends the buyer to `APP_URL/lists/<id>?token=<order ID>&PayerID=...` after approval, or with only `?token=` after a cancel ("Payment cancelled." is shown). `app/lists/[id]/list-context.tsx` handles both on every list tab.
5. **Capture.** The page posts to `POST /api/orders/{token}/capture`. The backend checks the ID's format (`400 INVALID_ORDER_ID`), that the order is one it created (`404 ORDER_NOT_FOUND`), then captures.
6. **Check off.** Only when the **capture's** status is `COMPLETED` — not the order's, since an order can be `COMPLETED` while its payment is `PENDING` or `DECLINED` (decision 25) — the backend marks the order `COMPLETED` with `captured_at`, and for each item sets `checked_at`, `bought_by` (the buyer), `price_cents` (the price stored at create time, so a change made while the buyer was on PayPal doesn't alter what is recorded as paid) and `order_id`.
   If the capture's status is `PENDING`, the order is stored as `PENDING`: Progress shows it with a **Check again** button and holds its items (decision 40). The button posts to `POST /api/orders/{id}/refresh`, which reads the order (`paypal.get_order()`, `GET /v2/checkout/orders/{id}`) and checks the items off if it has completed; any other status (declined, no capture) releases them.
7. **Clean up.** The page shows the result ("Paid. Those items are checked off.", or "Payment is pending; items stay unchecked for now."), then removes `?token=&PayerID=` from the address so a reload or a shared link can't capture again after PayPal's idempotency window.

## 4. Safety and edge cases

- **Money in cents.** All amounts are integer cents; `_usd()` turns them into PayPal's string amounts (`"12.50"`) without floats (decision 22).
- **Repeated capture.** The order ID is the capture's `PayPal-Request-Id`, so a retry, a refresh or React Strict Mode's double effect gets the first result. An item already checked off by this order is skipped.
- **Rate limits.** One retry on `429`, waiting for `Retry-After` but at most 5 seconds. The SDK's own retries are off (`max_retries=0`) so the wait stays capped. Calls time out after 30 seconds.
- **Errors.** PayPal errors become `PayPalError(status, issue)`. Capture answers `422 INSTRUMENT_DECLINED` when the buyer's funding source is declined (they can go back and pick another) and `502 PAYPAL_ERROR` for everything else, including network failures. Creating an order answers `502 PAYPAL_ERROR` on any failure.
- **One proof per item.** An item is proven bought by a PayPal order or by a receipt, never both (`items_one_proof` in `supabase/schema.sql`). If a receipt is confirmed while the buyer is on PayPal, the receipt keeps the item and the overlap is logged. Every check-off is a conditional update (`checked_at` still empty), so a capture and a receipt confirmed at the same moment can't overwrite each other.
- **Paid twice.** If a receipt or a hand tick got to an item first (decision 39): every unit was already bought, so the PayPal charge for that item is refunded to the buyer from the capture, whatever the quantity (`paypal.refund()`, `PayPal-Request-Id` = `<order ID>-<item ID>`, so a repeated capture refunds once), and recorded in `orders.refunds`. If the refund fails, the charge counts toward the buyer in the split (`boughtTwice`), so no money drops out of who-owes-whom.
- **Pending payments hold their items.** Items in a `PENDING` order can't be put in another order (`409 PAYMENT_PENDING`).
- **Paid items are locked.** An item with a PayPal order can't be unticked, re-priced, have its quantity changed, or be deleted (`409 ITEM_PAID`).
- **Old links.** Orders created when list pages lived at `/?list=<id>` still return there; `next.config.ts` redirects to `/lists/<id>` and keeps PayPal's query, so the capture still runs.
- **Credentials.** `PAYPAL_CLIENT_ID` and `PAYPAL_CLIENT_SECRET` are read only by the backend, from `.env.local` locally and from Render's secret variables when deployed. Missing credentials fail before any request is sent. See [RULES.md](RULES.md).

## 5. Where PayPal shows up in the app

| Page | What it shows |
|---|---|
| Progress | The Pay with PayPal button for the ticked items; the result after returning from PayPal |
| Progress, Items | What each item's status rests on: "Paid with PayPal", "On a receipt", "Marked bought by hand", "Payment pending at PayPal", plus who paid |
| Items | Each paid item's proof: "PayPal order <ID>" |
| Receipts | Every PayPal order on the list: ID, total, date, who paid, and the items it covered |
| Money | PayPal orders count toward what each person paid and the total spent |
| Settle up | Who pays whom (worked out from PayPal orders and receipts); **Pay Ann $X with PayPal** on each payment you owe, which sends the money to Ann's PayPal account; the payments made, with **Check again** for a pending one |

## 6. Planned, not built

- **Settle-up on the live sandbox** (decision 60, replacing the invoices of decision 9). Built and unit-tested: `POST /api/lists/{id}/settlements` creates an Orders API order with `purchase_units[0].payee.email_address` set to the PayPal email of the person owed, for the amount in the current split. The capture and **Check again** routes handle it like a list order, and a completed one counts in the split (`settlements` table). Still to check: that the sandbox accepts a **personal** account as the payee (it needs a second sandbox personal account). If it refuses, the person owed needs a sandbox business account.
- **JS SDK v6 buttons and webhooks, live:** built and unit-tested (decisions 66, 67). Still to try on the sandbox: the PayPal and Venmo pop-ups (Venmo needs the sandbox business account to have it, and a US buyer), and one webhook delivery to the Render URL.
- **Dark redesign.** The Figma draft puts a blue "Pay <name> with PayPal" button on each payment in Settle up ([ROADMAP](ROADMAP.md)). Built on the current design (decision 60).

## 7. Testing

- **Unit tests** never call PayPal. `backend/test_paypal.py` runs the real SDK against a fake HTTP session (`paypal.session`) and covers: price × quantity and the return URL in the create request, the capture's status (including a `COMPLETED` order with a `PENDING` payment), the 429 retry, PayPal errors carrying their issue and logging the `debug_id`, non-JSON error bodies, and missing credentials. `backend/test_main.py` covers the routes: database prices and quantities, items that can't be ordered, check-off at the stored price, receipts that got there first or at the same time, error codes, and the split after a payment. Run from `backend/`: `../../.venv/bin/python -m unittest`.
- **Live sandbox.** On 2026-10-26 the stored credentials got an OAuth token from `api-m.sandbox.paypal.com` (200). A captured order was checked on the list pages on 2026-10-15. Still to do: one full payment through the Pay button and back to `/lists/<id>`, which needs the owner to approve on PayPal's sandbox page (issue 25).

## 8. Setup

1. Create a sandbox app at [developer.paypal.com → Apps & Credentials (Sandbox)](https://developer.paypal.com/dashboard/applications/sandbox).
2. Put its client ID and secret in `.env.local` as `PAYPAL_CLIENT_ID` and `PAYPAL_CLIENT_SECRET`, and in Render's environment for the backend service. Never commit them.
3. Set `APP_URL` to the web app's address (default `http://localhost:3000`); PayPal sends buyers back there.
4. Pay with a sandbox **personal** (buyer) account from [Sandbox accounts](https://developer.paypal.com/dashboard/accounts). No real money moves.
